# 교차 출처 요청 허용 정책 — 기획 요구사항

## 배경 / 목적

co-browsing 세션 서버는 브라우저에서 동작하는 상담원 웹 콘솔과 고객 익스텐션이 호출한다. 브라우저는 한 출처(origin)에서 받은 페이지가 다른 출처의 서버를 호출할 때 보안상 응답을 차단하는 정책을 적용한다. 상담원 웹 콘솔은 세션 서버와 다른 출처에서 제공되므로, 서버는 허가된 웹 콘솔 출처에서 오는 요청만 브라우저가 정상 처리하도록 허용해야 한다. 그 외 임의의 웹사이트가 세션 서버 API를 브라우저에서 호출하는 것은 허용하지 않는다.

## 용어

- **출처(Origin)**: 웹 요청을 보낸 페이지의 출처를 식별하는 값으로, 프로토콜·도메인·포트의 조합이다. 예: `https://console.example.com`. 같은 도메인이라도 프로토콜이나 포트가 다르면 다른 출처다.
- **교차 출처 요청(Cross-Origin 요청)**: 페이지를 제공한 출처와 다른 출처의 서버로 보내는 브라우저 요청. 브라우저는 기본적으로 이런 요청의 응답을 호출 측에 노출하지 않도록 막는다.
- **교차 출처 허용 정책(CORS)**: 서버가 "어떤 출처의 브라우저 요청을 신뢰하는지"를 응답으로 알려, 브라우저가 그 응답을 호출 측에 노출해도 되는지 판단하게 하는 표준 정책.
- **허가된 웹 콘솔 출처(허용 목록)**: 운영자가 신뢰하기로 지정한 상담원 웹 콘솔의 출처 목록. 이 목록에 든 출처만 교차 출처 요청이 허용된다.
- **사전 확인 요청(Preflight)**: 브라우저가 본 요청을 보내기 전에, 그 요청이 허용되는지 서버에 미리 묻는 확인용 요청.

## 사용자 스토리 / 시나리오

- 상담원으로서, 허가된 웹 콘솔에서 세션 서버 API(시리얼 발급, TURN 자격증명 등)를 호출했을 때 브라우저가 응답을 정상적으로 받아 화면에 반영하기를 기대한다.
- 운영자로서, 신뢰하지 않는 임의의 웹사이트가 사용자의 브라우저를 통해 세션 서버 API를 호출하더라도 그 응답이 해당 웹사이트로 노출되지 않기를 기대한다.
- 운영자로서, 신뢰하는 웹 콘솔 출처 목록을 환경에 맞게(로컬 개발/운영) 지정하고 변경할 수 있기를 기대한다.

주요 흐름:

```
[허가된 웹 콘솔]
  브라우저 → (출처 표시) → 세션 서버
                              └─ 출처가 허용 목록에 있음 → 허용 응답 → 브라우저가 응답을 콘솔에 노출

[허가되지 않은 웹사이트]
  브라우저 → (출처 표시) → 세션 서버
                              └─ 출처가 허용 목록에 없음 → 허용 표시 없음 → 브라우저가 응답을 차단
```

## 기능 요구사항 (FR)

- FR-1. 시스템은 운영자가 신뢰하기로 지정한 웹 콘솔 출처의 목록(허용 목록)을 기준으로 교차 출처 요청 허용 여부를 판단해야 한다.
- FR-2. 시스템은 허용 목록에 포함된 출처에서 온 요청에 대해, 브라우저가 응답을 호출 측에 노출하도록 그 출처를 신뢰한다는 사실을 응답으로 알려야 한다.
- FR-3. 시스템은 허용 목록에 포함되지 않은 출처에서 온 요청에 대해, 그 출처를 신뢰한다는 표시를 응답에 포함하지 않아야 한다(브라우저가 응답을 차단하게 둔다).
- FR-4. 시스템은 본 요청 이전에 도착하는 사전 확인 요청(Preflight)에 대해, 허용된 방식·항목을 알리고 본 처리를 진행하지 않고 즉시 응답해야 한다.
- FR-5. 시스템은 허용 목록을 운영 환경에 따라 지정할 수 있어야 하며, 별도 지정이 없을 때는 로컬 개발용 출처를 기본으로 사용해야 한다.
- FR-6. 시스템은 여러 개의 허용 출처를 동시에 지정할 수 있어야 하며, 지정된 모든 출처를 각각 허용해야 한다.

## 규칙 / 제약 (비즈니스 룰)

- 출처 일치는 정확 일치로 판단한다. 프로토콜·도메인·포트가 모두 같아야 같은 출처로 본다. 부분 일치나 하위 도메인 자동 포함은 하지 않는다.
- "모든 출처 허용"(전체 와일드카드)은 사용하지 않는다. 신뢰하는 출처는 항상 명시적으로 지정된 목록으로만 결정된다.
- 허용된 출처에서 온 요청은 인증/자격 정보를 동반한 교차 출처 요청도 정상 처리될 수 있어야 한다. 이를 위해 신뢰 표시는 요청한 그 출처를 그대로 가리키며, 전체 와일드카드로 대체하지 않는다.
- 이 정책은 브라우저가 출처 정보를 실어 보내는 일반 API 호출에 적용된다. 실시간 연결(WebSocket) 수립 자체는 브라우저의 교차 출처 차단 대상이 아니므로, 이 정책으로 연결 수립이 막히거나 영향을 받지 않는다.
- 출처 정보가 없는 요청(브라우저가 아닌 호출 등)은 이 정책의 허용/차단 판단 대상이 아니며 정상 처리한다.

## 비기능 요구사항 (NFR)

- NFR-1. 허용 목록은 운영 환경별로(로컬 개발/스테이징/운영) 코드 변경 없이 설정으로 바꿀 수 있어야 한다.
- NFR-2. 이 정책은 세션 서버의 모든 API 요청에 일관되게 적용되어야 한다(특정 엔드포인트만 예외로 두지 않는다).
- NFR-3. 신뢰 판단의 기준은 운영자가 명시한 허용 목록뿐이며, 임의 출처가 스스로를 신뢰 대상으로 만들 수 없어야 한다.

## 인수 조건 (Acceptance Criteria)

- [ ] AC-1. (Given 허용 목록에 `http://localhost:3000`이 있고) (When 출처 `http://localhost:3000`에서 API를 호출하면) (Then 응답이 그 출처를 신뢰한다고 표시되어 브라우저가 응답을 호출 측에 노출한다.)
- [ ] AC-2. (Given 허용 목록에 없는 출처에서) (When API를 호출하면) (Then 응답에 그 출처를 신뢰한다는 표시가 없어 브라우저가 응답을 차단한다.)
- [ ] AC-3. (Given 어떤 API 경로에 대해) (When 사전 확인 요청(Preflight)이 도착하면) (Then 본 처리를 진행하지 않고 허용 정보를 담아 즉시 응답한다.)
- [ ] AC-4. (Given 허용 목록을 `https://a.example.com`과 `https://b.example.com` 두 출처로 지정하면) (When 각 출처에서 호출하면) (Then 두 출처 모두 신뢰 표시를 받아 허용된다.)
- [ ] AC-5. (Given 허용 목록을 별도로 지정하지 않으면) (When 기본 로컬 개발 출처에서 호출하면) (Then 그 출처가 허용된다.)
- [ ] AC-6. (Given 허용 목록에 든 출처에서) (When 호출하면) (Then 신뢰 표시는 "모든 출처 허용"(와일드카드)이 아니라 요청한 그 출처를 정확히 가리킨다.)
