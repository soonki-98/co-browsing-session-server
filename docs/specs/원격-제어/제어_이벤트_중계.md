# 제어 이벤트 중계 — 기획 요구사항

## 배경 / 목적

고객 지원(CS) 상황에서 상담원은 고객의 말만으로 문제를 파악하기 어렵고, 고객은 안내받은 화면 조작을 그대로 따라 하기 어렵다. 상담원이 고객 화면을 함께 보며 직접 마우스를 움직이고 클릭·스크롤·키 입력을 대신 수행할 수 있으면, 말로 설명하는 대신 손으로 보여 주는 원격 안내가 가능해진다. 이 요구사항은 상담원이 만든 제어 동작을 고객 화면으로 전달해 그대로 재현되게 하는 것을 다룬다.

## 용어

- **룸 세션(room session)**: 한 고객과 한 상담원이 같은 화면을 공유하는 하나의 연결 단위.
- **고객(customer)**: 자신의 화면을 공유하고, 상담원의 제어 동작을 자신의 화면에서 받아 재현하는 쪽.
- **상담원(agent)**: 고객 화면을 보며 원격으로 제어 동작을 만들어 보내는 쪽.
- **제어 동작(제어 이벤트)**: 상담원이 고객 화면을 조작하기 위해 보내는 한 번의 마우스/키보드 입력. 예: 특정 위치 클릭, 화면 스크롤, 키 입력.
- **발생 시각**: 그 제어 동작이 일어난 시점. 동작의 순서·재현 타이밍을 위해 함께 전달된다.

## 사용자 스토리 / 시나리오

- 상담원으로서, 고객 화면의 특정 버튼을 직접 눌러 주기 위해 그 위치를 클릭하는 제어 동작을 보낸다.
- 상담원으로서, 고객이 봐야 할 영역을 보여 주기 위해 화면을 스크롤하는 제어 동작을 보낸다.
- 상담원으로서, 입력란을 대신 채워 주기 위해 키 입력 제어 동작을 보낸다.
- 고객으로서, 상담원이 보낸 제어 동작이 내 화면에서 그대로 재현되어 안내받는 대로 화면이 움직이는 것을 본다.

주요 흐름(사용자 관점):

```
상담원이 제어 동작 수행
        │
        ▼
서버가 동작을 받아 (보낸 사람이 상담원인지, 종류가 허용되는지) 확인
        │
        ├─ 거부 사유 있음 ─▶ 상담원에게 거부 안내
        │
        ▼ 통과
서버가 발생 시각을 보완(누락 시)
        │
        ▼
고객 화면으로 동작 전달 → 고객 화면에서 재현
```

## 기능 요구사항 (FR)

- FR-1. 시스템은 상담원이 보낸 제어 동작을 같은 룸 세션의 고객에게 전달해야 한다.
- FR-2. 시스템은 마우스 클릭, 화면 스크롤, 키 입력 세 종류의 제어 동작을 전달 대상으로 지원해야 한다.
- FR-3. 시스템은 위 세 종류에 속하지 않는 종류의 제어 동작은 전달하지 않고 거부하며, 보낸 상담원에게 거부 사실을 알려야 한다.
- FR-4. 시스템은 제어 동작에 발생 시각이 함께 들어 있지 않으면, 전달 전에 서버가 그 동작을 처리하는 시점의 시각으로 발생 시각을 채워 넣어야 한다.
- FR-5. 시스템은 제어 동작에 발생 시각이 이미 들어 있으면 그 값을 그대로 유지해야 한다.
- FR-6. 시스템은 제어 동작 전달 방향을 상담원에서 고객으로만 허용해야 한다. 고객이 제어 동작을 보내면 전달하지 않고 거부하며, 보낸 고객에게 거부 사실을 알려야 한다.
- FR-7. 시스템은 고객이 아직 접속해 있지 않은 상태에서 상담원이 제어 동작을 보내면 전달하지 않고, 상대가 연결되어 있지 않다는 사실을 상담원에게 알려야 한다.
- FR-8. 시스템은 고객에게 전달하는 제어 동작에 동작의 종류와 그 종류에 해당하는 위치/방향/키 정보, 그리고 발생 시각을 함께 포함해야 한다.

## 규칙 / 제약 (비즈니스 룰)

- 제어 동작의 전달 방향은 항상 상담원 → 고객 한 방향이다. 반대 방향(고객 → 상담원)은 존재하지 않으며, 고객이 보낸 제어 동작은 거부된다.
- 전달 가능한 제어 동작의 종류는 마우스 클릭, 화면 스크롤, 키 입력으로 한정한다. 그 외 종류는 알 수 없는 종류로 보고 거부한다.
- 거부되는 경우(상담원이 아님 / 고객 미접속 / 허용되지 않은 종류)에는 동작이 고객에게 전달되지 않고, 보낸 쪽이 어떤 사유로 거부됐는지 구분해 알 수 있어야 한다.
  - 권한 거부: 상담원이 아닌 쪽(고객)이 제어 동작을 보낸 경우.
  - 상대 미접속: 보낼 대상인 고객이 아직 접속해 있지 않은 경우.
  - 종류 거부: 허용되지 않은 종류의 제어 동작인 경우.
- 발생 시각 보완은 "값이 없을 때만" 적용한다. 상담원이 보낸 발생 시각이 있으면 서버가 덮어쓰지 않는다.
- 각 종류별로 의미 있는 부가 정보(클릭/스크롤은 위치·방향, 키 입력은 어떤 키인지)는 동작과 함께 전달된다. 이번 범위에서는 부가 정보의 누락 여부까지 서버가 검증하지는 않으며, 동작의 종류가 허용되는지만 확인한다.
- 전달되는 제어 동작에는 그 종류에 해당하지 않는 빈 정보는 포함하지 않는다(예: 클릭 동작에 키 정보를 끼워 넣지 않는다).

## 비기능 요구사항 (NFR)

- 제어 동작 전달은 상담원의 조작과 고객 화면 재현 사이의 지연이 작아야 하며, 동작의 순서가 보존되어야 한다.
- 여러 룸 세션이 동시에 진행돼도 한 세션의 제어 동작이 다른 세션의 고객에게 새어 나가지 않아야 한다(동작은 항상 같은 세션의 상대에게만 전달된다).
- 제어 동작 처리 중 한쪽이 보낸 잘못된/허용되지 않은 동작이 세션 전체를 끊거나 상대에게 영향을 주지 않아야 한다 — 거부는 보낸 쪽에 대한 안내로 끝난다.

## 인수 조건 (Acceptance Criteria)

- [ ] AC-1. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 상담원이 위치 정보를 포함한 클릭 제어 동작을 보내면) (Then 고객이 동일한 클릭 동작을 같은 위치 정보와 함께 전달받는다.)
- [ ] AC-2. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 상담원이 발생 시각 없이 제어 동작을 보내면) (Then 고객이 전달받은 동작에는 서버가 처리한 시점의 발생 시각이 채워져 있다.)
- [ ] AC-3. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 상담원이 발생 시각을 포함해 제어 동작을 보내면) (Then 고객이 전달받은 동작의 발생 시각은 상담원이 보낸 값과 동일하다.)
- [ ] AC-4. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 고객이 제어 동작을 보내면) (Then 그 동작은 상담원에게 전달되지 않고, 고객은 권한 거부 안내를 받는다.)
- [ ] AC-5. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 상담원이 허용되지 않은 종류의 제어 동작을 보내면) (Then 그 동작은 고객에게 전달되지 않고, 상담원은 허용되지 않은 종류라는 거부 안내를 받는다.)
- [ ] AC-6. (Given 상담원만 접속해 있고 고객은 아직 접속하지 않았으며) (When 상담원이 제어 동작을 보내면) (Then 그 동작은 전달되지 않고, 상담원은 상대가 접속해 있지 않다는 안내를 받는다.)
- [ ] AC-7. (Given 고객과 상담원이 같은 세션에 접속해 있고) (When 상담원이 마우스 클릭, 화면 스크롤, 키 입력 각각을 보내면) (Then 세 종류 모두 고객에게 전달되며, 각 동작에는 그 종류에 맞는 부가 정보가 포함된다.)
- [ ] AC-8. (Given 거부되는 제어 동작이 발생했을 때) (When 권한 거부 / 상대 미접속 / 허용되지 않은 종류 중 어느 경우든) (Then 보낸 쪽은 세 사유를 서로 구분할 수 있는 형태로 거부 안내를 받는다.)
