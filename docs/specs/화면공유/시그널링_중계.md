# 시그널링 중계 — 기획 요구사항

## 배경 / 목적

고객과 상담원이 화면을 공유하려면, 두 사람의 브라우저가 서로 직접(P2P) 연결돼야 한다. 하지만 두 브라우저는 처음엔 상대가 어디 있는지, 어떤 방식으로 연결할 수 있는지를 모른다. 직접 연결을 맺기 위해 양쪽이 주고받아야 하는 "연결 협상 정보"를 서버가 가운데에서 충실히 전달해 주는 것이 시그널링 중계다.

서버는 이 정보를 들여다보거나 바꾸지 않는다. 양쪽 사이에서 정확한 상대에게, 정해진 순서·역할 규칙에 맞게 전달만 한다. 잘못되거나 관계없는 정보는 전달하지 않는다.

## 용어

- **고객 / 상담원**: 같은 세션(룸)에 합류한 두 참여자. 고객은 자기 화면을 공유하는 쪽, 상담원은 그 화면을 받아 보는 쪽이다.
- **P2P(직접 연결)**: 서버를 거치지 않고 고객 브라우저와 상담원 브라우저가 직접 화면 데이터를 주고받는 연결.
- **화면공유 기술(WebRTC)**: 브라우저가 자체적으로 P2P 화면/영상 연결을 맺는 데 쓰는 표준 기술. 이 연결을 맺으려면 아래 두 종류의 협상 정보를 양쪽이 교환해야 한다.
- **연결 제안 / 연결 응답(SDP offer / answer)**: 한쪽이 "이런 방식으로 연결하자"고 제안하면(연결 제안), 다른 한쪽이 "그 방식으로 연결하겠다"고 답한다(연결 응답). 이 한 쌍이 오가야 연결의 기본 규격이 맞춰진다.
- **연결 경로 후보(ICE candidate)**: 두 브라우저가 실제로 어떤 네트워크 경로로 닿을 수 있는지에 대한 후보 정보. 양쪽이 여러 개를 주고받아 실제 통할 경로를 함께 찾아낸다.
- **상대방(peer)**: 같은 세션에서 메시지를 보낸 사람의 반대편 참여자. 고객의 상대방은 상담원이고, 상담원의 상대방은 고객이다.

## 사용자 스토리 / 시나리오

- 고객으로서, 내 화면을 상담원에게 보여주기 위해 화면 공유 연결을 시작한다.
- 상담원으로서, 고객 화면을 받아 보기 위해 고객이 보낸 연결 제안에 응답한다.

주요 흐름(사용자 관점):

```
고객                         서버(중계)                      상담원
 │  연결 제안 ───────────────▶  │                              │
 │                             │ ── 그대로 상담원에게 전달 ──▶  │
 │                             │                              │ 연결 응답 생성
 │                             │  ◀──────────── 연결 응답 ──── │
 │  ◀── 그대로 고객에게 전달 ── │                              │
 │                             │                              │
 │  연결 경로 후보 ◀──────────▶ │ ◀──────────▶ 연결 경로 후보   │   (양방향, 여러 번)
 │                             │                              │
 └──── 직접(P2P) 화면 공유 연결 수립 ──────────────────────────┘
```

연결 제안·응답이 한 차례 오가고, 연결 경로 후보가 양방향으로 충분히 교환되면, 두 브라우저는 서버를 거치지 않는 직접 연결을 맺어 화면 공유를 시작한다.

## 기능 요구사항 (FR)

- FR-1. 시스템은 한 참여자가 보낸 연결 협상 정보(연결 제안 / 연결 응답 / 연결 경로 후보)를 같은 세션의 상대방에게 전달해야 한다.
- FR-2. 시스템은 고객이 보낸 연결 제안을 상담원에게 전달해야 한다.
- FR-3. 시스템은 상담원이 보낸 연결 응답을 고객에게 전달해야 한다.
- FR-4. 시스템은 연결 경로 후보를 어느 쪽이 보냈든 상대방에게 전달해야 한다.
- FR-5. 시스템은 협상 정보의 내용을 들여다보거나 수정하지 않고, 보낸 그대로 상대방에게 전달해야 한다.
- FR-6. 시스템은 상대방이 아직 세션에 합류하지 않은 상태에서 협상 정보가 도착하면, 그 정보를 전달하지 않고 보낸 사람에게 "상대방이 아직 연결되지 않았다"는 안내를 돌려줘야 한다.
- FR-7. 시스템은 역할에 맞지 않는 협상 정보(상담원이 보낸 연결 제안, 고객이 보낸 연결 응답)는 전달하지 않고, 보낸 사람에게 "보낸 주체가 잘못됐다"는 안내를 돌려줘야 한다.

## 규칙 / 제약 (비즈니스 룰)

- **연결 제안은 고객만 보낸다.** 상담원이 연결 제안을 보내면 전달되지 않고, 보낸 상담원에게 잘못된 요청이라는 안내가 돌아간다.
- **연결 응답은 상담원만 보낸다.** 고객이 연결 응답을 보내면 전달되지 않고, 보낸 고객에게 잘못된 요청이라는 안내가 돌아간다.
- **연결 경로 후보는 양쪽 모두 보낼 수 있다.** 보낸 주체에 대한 역할 제한이 없으며, 항상 상대방에게 전달된다.
- **상대방이 없으면 중계하지 않는다.** 같은 세션에 상대방이 아직 합류하지 않았다면 어떤 협상 정보도 전달되지 않고, 보낸 사람에게만 안내가 돌아간다.
- **내용 보존.** 협상 정보는 서버가 해석·가공하지 않고 받은 그대로 전달한다. 중계 과정에서 값이 바뀌어선 안 된다(연결 규격·경로 정보가 한 글자라도 달라지면 직접 연결이 실패할 수 있다).
- **안내는 보낸 사람에게만.** 거부(상대방 미접속 / 잘못된 주체)에 대한 안내는 그 메시지를 보낸 당사자에게만 돌아가고, 상대방에게는 아무것도 전달되지 않는다.
- **관계없는 정보는 중계 대상이 아니다.** 연결 제안·연결 응답·연결 경로 후보 외의 메시지는 이 중계 규칙의 대상이 아니며, 시그널링으로 전달되지 않는다.

## 비기능 요구사항 (NFR)

- **투명성.** 서버는 협상 정보의 내용을 저장·로깅·변형하지 않는다. 받은 그대로 흘려보내는 통로 역할만 한다.
- **동시성 안전.** 여러 세션이 동시에 시그널링을 주고받아도 각 세션의 협상 정보가 서로 섞이지 않고, 항상 같은 세션의 상대방에게만 전달된다.
- **즉시성.** 한쪽이 보낸 협상 정보는 별도 지연 없이 상대방에게 곧바로 전달된다(직접 연결 수립 시간을 늘리지 않는다).

## 인수 조건 (Acceptance Criteria)

- [ ] AC-1. (Given 고객과 상담원이 같은 세션에 합류해 있을 때) (When 고객이 연결 제안을 보내면) (Then 상담원이 그 연결 제안을 받는다.)
- [ ] AC-2. (Given 고객과 상담원이 같은 세션에 합류해 있을 때) (When 상담원이 연결 응답을 보내면) (Then 고객이 그 연결 응답을 받는다.)
- [ ] AC-3. (Given 고객과 상담원이 같은 세션에 합류해 있을 때) (When 어느 한쪽이 연결 경로 후보를 보내면) (Then 상대방이 그 후보를 받는다. 양방향 모두 성립한다.)
- [ ] AC-4. (Given 상담원이 아직 세션에 합류하지 않았을 때) (When 고객이 연결 제안을 보내면) (Then 연결 제안은 전달되지 않고, 고객은 "상대방이 아직 연결되지 않았다"는 안내를 받는다.)
- [ ] AC-5. (Given 고객과 상담원이 같은 세션에 합류해 있을 때) (When 상담원이 연결 제안을 보내면) (Then 연결 제안은 고객에게 전달되지 않고, 상담원은 "보낸 주체가 잘못됐다"는 안내를 받는다.)
- [ ] AC-6. (Given 고객과 상담원이 같은 세션에 합류해 있을 때) (When 고객이 연결 응답을 보내면) (Then 연결 응답은 상담원에게 전달되지 않고, 고객은 "보낸 주체가 잘못됐다"는 안내를 받는다.)
- [ ] AC-7. (Given 어떤 협상 정보가 한쪽에서 다른 쪽으로 중계될 때) (When 상대방이 그 정보를 받으면) (Then 받은 내용은 보낸 내용과 완전히 동일하다. 어떤 값도 변형되지 않는다.)
- [ ] AC-8. (Given 거부(상대방 미접속 또는 잘못된 주체)가 발생할 때) (When 보낸 사람에게 안내가 돌아갈 때) (Then 상대방은 그 메시지와 안내를 전혀 받지 않는다.)
