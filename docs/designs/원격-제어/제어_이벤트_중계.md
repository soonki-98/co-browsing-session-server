# 제어 이벤트 중계 — 기술 설계도

> 기획: [docs/specs/원격-제어/제어_이벤트_중계.md](../../specs/원격-제어/제어_이벤트_중계.md)

## Overview

상담원(agent)이 만든 마우스/키보드 제어 동작을 같은 룸 세션의 고객(customer)에게 단방향으로 중계한다. WebSocket 메시지 타입 `control-event`를 수신하면 (1) 발신자가 상담원인지 검증하고, (2) 고객이 접속해 있는지 확인하고, (3) 이벤트 종류(`click`/`scroll`/`keydown`)가 허용되는지 검증하고, (4) 발생 시각(`timestamp`)이 비어 있으면 서버 처리 시점으로 보완한 뒤, (5) 고객에게 재직렬화해 전달한다. 거부 사유는 `FORBIDDEN`/`INVALID_EVENT_TYPE`/`PEER_NOT_CONNECTED` 세 가지로 구분해 발신자에게 error 메시지로 회신한다.

현재 `internal/interfaces/ws/ws.go`의 `readPump`는 `control-event`를 시그널링 메시지와 묶어 raw 바이트 그대로 상대에게 흘려 보내는 **passthrough TODO** 상태다(`TODO(step5/6)`). 이 설계도는 그 TODO를 본 기능으로 대체하는 기준을 규정한다 — role 검증, 종류 검증, 타임스탬프 보완, 단방향 라우팅을 전용 유즈케이스 흐름으로 분리한다.

레이어 배치는 실제 프로젝트 구조를 따른다: WebSocket 어댑터는 `internal/interfaces/ws`, 제어 이벤트의 비즈니스 흐름(검증·보완·라우팅 결정)은 services 레이어의 전용 유즈케이스에 둔다. 어댑터는 바이트 ↔ DTO 직렬화와 펌프만, 규칙은 services가 책임진다(루트·interfaces·services `CLAUDE.md`의 의존 규칙).

## Implementation Order

```
[1] 세션 스토어            ✓
[2] 룸 생성 (POST /rooms)   ✓
[3] WebSocket Hub          ✓
[4] WebSocket Handler      ✓ (control-event는 현재 passthrough TODO)
[5] 시그널링 프로토콜       (예정)
[6] 제어 이벤트 중계        ← 본 설계
[7] TURN 자격증명           (예정)
[8] CORS 미들웨어           (예정)
```

- **선행 의존:** `#3 WebSocket Hub`(`hub.Client`/`hub.Role`/peer 조회), `#4 WebSocket Handler`(`readPump`의 `control-event` 분기·`Message`/`marshalMessage`/`sendError` 헬퍼·`connection.Coordinator.Peer`)
- **후행 의존:** 없음

## Layer Mapping

| 책임 | 레이어 | 위치 |
|------|--------|------|
| `control-event` 수신·DTO 파싱·error/전달 메시지 직렬화·peer 조회 | interfaces (ws 어댑터) | `internal/interfaces/ws/ws.go`, `internal/interfaces/ws/dto.go` |
| 제어 이벤트 유즈케이스 — 발신자 검증, 종류 검증, 타임스탬프 보완, 라우팅 대상 결정 | services | `internal/services/relay`(신규) |
| 라이브 연결 상태(상대방 조회) | services (Hub/Coordinator) | `internal/services/hub`, `internal/services/connection` |
| 룸 안 역할 식별 (`hub.Role`: customer/agent) | services (Hub) | `internal/services/hub/hub.go` |

의존 방향: interfaces → services → (domain). services는 interfaces/infrastructure/app을 import하지 않는다. 제어 이벤트 페이로드 DTO와 종류 검증·타임스탬프 보완 규칙은 services(`relay`)에 두고, ws 어댑터는 raw payload를 services에 위임하고 결과(전달/거부)를 프로토콜 메시지로 직렬화만 한다. `relay`는 `hub`(같은 services 레이어)에만 의존한다 — depguard 위반 없음.

## Data Structures

제어 이벤트 페이로드 DTO — services `relay` 패키지에 자체 정의한다. ws 어댑터의 `Message.Payload`(`json.RawMessage`)를 그대로 위임받아 파싱하므로, interfaces DTO와 별개의 Go 타입이어도 변환 비용이 없다(의존 방향 보존).

```go
// internal/services/relay/control.go
package relay

// ControlEventPayload는 control-event 메시지의 payload다.
// 종류(Type)에 따라 의미 있는 부가 필드만 채워지며, 나머지는 omitempty로 직렬화에서 제외된다.
type ControlEventPayload struct {
    Type      string  `json:"type"`             // "click" | "scroll" | "keydown"
    X         *int    `json:"x,omitempty"`
    Y         *int    `json:"y,omitempty"`
    Key       *string `json:"key,omitempty"`
    DeltaY    *int    `json:"deltaY,omitempty"`
    Timestamp int64   `json:"timestamp"`        // Unix milliseconds, 0이면 서버가 보완
}
```

허용 종류 집합 — 패키지 레벨 불변 룩업:

```go
// internal/services/relay/control.go
var allowedControlEventTypes = map[string]bool{
    "click":   true,
    "scroll":  true,
    "keydown": true,
}
```

ws 어댑터의 메시지 래퍼와 error 페이로드는 기존 타입을 그대로 재사용한다(신규 정의 아님):

```go
// internal/interfaces/ws/dto.go (기존)
type Message struct {
    Type    string          `json:"type"`
    Payload json.RawMessage `json:"payload,omitempty"`
}

type ErrorPayload struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}

const msgTypeControlEvent = "control-event" // 기존 상수
```

## Interfaces / Contracts

services `relay`의 유즈케이스 — 검증·보완을 수행하고 결과(고객에게 보낼 바이트 또는 거부 사유)를 돌려준다. 채널 송신·소켓 쓰기는 어댑터의 책임이므로, `relay`는 순수하게 "무엇을 보낼지"만 결정해 반환한다(테스트 용이성·의존 방향 보존).

```go
// internal/services/relay/control.go
package relay

// RejectionCode는 제어 이벤트가 거부된 사유다. error 메시지의 code로 전달된다.
type RejectionCode string

const (
    RejectForbidden       RejectionCode = "FORBIDDEN"            // 발신자가 상담원이 아님
    RejectInvalidType     RejectionCode = "INVALID_EVENT_TYPE"   // 허용되지 않은 종류
    RejectPeerNotConnected RejectionCode = "PEER_NOT_CONNECTED"  // 고객 미접속
)

// Result는 제어 이벤트 처리 결과다.
// Rejected가 true면 Code/Message로 발신자에게 거부를 회신하고 전달하지 않는다.
// false면 Outbound를 고객에게 전달한다.
type Result struct {
    Rejected bool
    Code     RejectionCode
    Message  string
    Outbound []byte // 고객에게 보낼 {"type":"control-event","payload":{...}} 직렬화 바이트
}

// HandleControlEvent는 control-event 한 건을 처리한다.
//   senderRole: 메시지를 보낸 클라이언트의 역할 (반드시 RoleAgent여야 통과)
//   peer:       상대방 클라이언트 (nil이거나 고객이 아니면 PEER_NOT_CONNECTED)
//   rawPayload: control-event의 payload JSON
func HandleControlEvent(senderRole hub.Role, peer *hub.Client, rawPayload json.RawMessage) Result
```

ws 어댑터 계약(기존 `readPump`의 `control-event` 분기를 대체):

```go
// internal/interfaces/ws/ws.go
// case msgTypeControlEvent: 발신 client.Role과 coordinator.Peer(client)를 넘겨 relay에 위임,
// Result.Rejected면 sendError(client, code, message), 아니면 trySend(peer, Result.Outbound).
```

## Behavior

### 처리 흐름 (ws 어댑터 + relay 유즈케이스)

```go
// readPump 안에서 control-event 수신 시
case msgTypeControlEvent:
    peer := handler.coordinator.Peer(client)
    result := relay.HandleControlEvent(client.Role, peer, incoming.Payload)
    if result.Rejected {
        sendError(client, string(result.Code), result.Message)
        continue
    }
    trySend(peer, result.Outbound)
```

`relay.HandleControlEvent`의 순서:

```go
func HandleControlEvent(senderRole hub.Role, peer *hub.Client, rawPayload json.RawMessage) Result {
    // 1. 발신자 검증 — 상담원만 제어 동작을 보낼 수 있다 (단방향 상담원 → 고객).
    if senderRole != hub.RoleAgent {
        return Result{Rejected: true, Code: RejectForbidden,
            Message: "only agent can send control events"}
    }

    // 2. 고객 연결 확인 — 상대가 없거나 고객이 아니면 전달 대상이 없다.
    if peer == nil || peer.Role != hub.RoleCustomer {
        return Result{Rejected: true, Code: RejectPeerNotConnected,
            Message: "customer is not connected"}
    }

    // 3. payload 파싱.
    var evt ControlEventPayload
    if err := json.Unmarshal(rawPayload, &evt); err != nil {
        return Result{Rejected: true, Code: RejectInvalidType,
            Message: "malformed control event payload"}
    }

    // 4. 이벤트 종류 검증 — click/scroll/keydown만 허용. 그 외는 거부.
    if !allowedControlEventTypes[evt.Type] {
        return Result{Rejected: true, Code: RejectInvalidType,
            Message: "unknown control event type: " + evt.Type}
    }

    // 5. 타임스탬프 보완 — 0(미설정)일 때만 서버 처리 시점으로 채운다. 값이 있으면 보존.
    if evt.Timestamp == 0 {
        evt.Timestamp = time.Now().UnixMilli()
    }

    // 6. 고객에게 보낼 메시지 직렬화 — omitempty로 종류에 맞는 필드만 포함.
    outbound := marshalControlEvent(evt)
    return Result{Outbound: outbound}
}
```

`marshalControlEvent`는 `relay` 패키지 내부 헬퍼로, `{"type":"control-event","payload":{...}}` 형태로 직렬화한다(interfaces의 `marshalMessage`와는 별개 — 의존 방향 보존).

### 이벤트 종류 검증 (click / scroll / keydown)

- 허용 종류는 `click`, `scroll`, `keydown` 세 가지로 한정한다. `allowedControlEventTypes` 룩업에 없으면 `INVALID_EVENT_TYPE`로 거부한다.
- 종류별 의미 있는 부가 필드(클릭/스크롤의 위치·방향, 키 입력의 키)는 함께 전달되나, **MVP 범위에서 부가 필드의 누락은 검증하지 않는다**(클라이언트 책임). 서버는 종류 허용 여부만 확인한다.

| 종류 | 주 필드 | 비고 |
|------|---------|------|
| `click` | `x`, `y` | 위치 |
| `scroll` | `deltaY` (+ `x`,`y`) | 방향/위치 |
| `keydown` | `key` | 입력 키 |

- 포인터 필드 + `omitempty`로, 그 종류에 해당하지 않는 빈 정보(예: 클릭에 `key`)는 전달 JSON에서 제외된다.

### 서버 타임스탬프 보완 (0일 때만)

- `Timestamp == 0`(상담원이 보내지 않음)일 때만 `time.Now().UnixMilli()`로 채운다.
- 상담원이 `Timestamp`를 보냈으면(0이 아니면) 서버는 **덮어쓰지 않고 그대로 보존**한다.
- 보완이 필요하므로 SDP처럼 raw 통과시키지 않고 **재직렬화**해 전달한다.

### 단방향 라우팅 (상담원 → 고객)

- 발신자 역할이 `RoleAgent`가 아니면(즉 고객이 보내면) `FORBIDDEN`으로 거부한다. 고객 → 상담원 방향은 존재하지 않는다.
- 전달 대상은 항상 같은 룸 세션의 상대 — `coordinator.Peer(client)`(Hub의 `GetPeer`)로 조회한다. 다른 세션으로 새지 않는다.

### 거부 처리 (FORBIDDEN / INVALID_EVENT_TYPE / PEER_NOT_CONNECTED)

- 거부 시 고객에게 전달하지 않고, 발신자에게만 `{"type":"error","payload":{"code":...,"message":...}}`(어댑터의 `sendError`)로 사유를 구분해 회신한다.
- 거부는 발신자 안내로 끝나며 세션을 끊거나 상대에게 영향을 주지 않는다 — `continue`로 다음 메시지를 계속 읽는다.

| 사유 | code | 조건 |
|------|------|------|
| 권한 거부 | `FORBIDDEN` | 발신자가 상담원이 아님(고객이 보냄) |
| 종류 거부 | `INVALID_EVENT_TYPE` | 허용 종류(click/scroll/keydown)가 아님 / payload 파싱 실패 |
| 상대 미접속 | `PEER_NOT_CONNECTED` | peer가 nil이거나 고객이 아님 |

### 고객이 수신하는 메시지 형식

```json
{
  "type": "control-event",
  "payload": {
    "type": "click",
    "x": 320,
    "y": 240,
    "timestamp": 1716000000000
  }
}
```

## Test Plan

테이블 기반 + named subtest(`t.Run`), 독립 케이스는 `t.Parallel()`. services `relay` 유즈케이스는 순수 함수에 가까워 단위 테스트로 검증하고, 어댑터 통합은 `httptest.Server` + 실제 WebSocket dial로 확인한다(`go test -race`).

services `relay` 단위 테스트 (`internal/services/relay/control_test.go`):

- 상담원이 위치 포함 `click` 전송 → `Rejected=false`, Outbound payload에 동일 `x`/`y` 포함 (AC-1, AC-7)
- `Timestamp` 0으로 전송 → Outbound의 timestamp가 0이 아닌 현재 시각(Unix ms)으로 보완 (AC-2)
- `Timestamp` 지정해 전송 → Outbound timestamp가 입력값과 동일(보존) (AC-3)
- 발신자 `RoleCustomer` → `Rejected=true`, `Code=FORBIDDEN` (AC-4, AC-8)
- `Type="hover"` 등 미허용 종류 → `Rejected=true`, `Code=INVALID_EVENT_TYPE` (AC-5, AC-8)
- `peer == nil`(고객 미접속) / peer가 고객 아님 → `Rejected=true`, `Code=PEER_NOT_CONNECTED` (AC-6, AC-8)
- `scroll`(deltaY)·`keydown`(key) 각각 → 통과 + 종류에 맞는 필드만 포함, 무관 필드는 omitempty로 제외 (AC-7)
- 잘못된 JSON payload → `INVALID_EVENT_TYPE`로 거부, 패닉 없음

interfaces `ws` 통합 테스트:

- 같은 세션의 상담원·고객 dial 후 상담원이 control-event 전송 → 고객 소켓이 동일 payload + timestamp 수신 (AC-1)
- 고객이 control-event 전송 → 고객 소켓이 `error`/`FORBIDDEN` 수신, 상담원에게 전달 안 됨 (AC-4)
- 미허용 종류 → 상담원 소켓이 `error`/`INVALID_EVENT_TYPE` 수신 (AC-5)
- 고객 미접속 상태에서 상담원 전송 → 상담원 소켓이 `error`/`PEER_NOT_CONNECTED` 수신 (AC-6)
- 거부 후에도 연결이 유지되어 후속 정상 이벤트가 정상 전달됨(거부가 세션을 끊지 않음, NFR)
