# 시그널링 중계 — 기술 설계도

> 기획: [docs/specs/화면공유/시그널링_중계.md](../../specs/화면공유/시그널링_중계.md)

## Overview

WebRTC P2P 연결 수립에 필요한 SDP `offer`/`answer`와 ICE `candidate`를, 같은 세션(LiveRoom)에 합류한 고객과 상담원 사이에서 **서버가 내용을 들여다보거나 변형하지 않고 그대로 중계**하는 시그널링 로직이다. 서버는 통로(transparent relay) 역할만 하며, 메시지 타입과 발신자 역할에 따라 정확한 상대방(peer)에게만 전달한다.

이 설계의 핵심 기술 결정 세 가지:

1. **원문 보존(transparent relay).** SDP/ICE 페이로드는 브라우저 WebRTC API가 만들고 소비하는 불투명 데이터다. 서버는 페이로드를 재파싱·재직렬화하지 않고 `ReadMessage`가 돌려준 **원본 바이트(raw)** 를 그대로 peer의 송신 채널에 넣는다. 한 글자라도 달라지면 직접 연결이 실패할 수 있기 때문이다.
2. **역할 기반 발신자 검증.** `offer`는 고객만, `answer`는 상담원만 보낼 수 있다. `ice-candidate`는 양쪽 모두 허용한다. 역할에 맞지 않으면 중계하지 않고 발신자에게만 에러를 돌려준다.
3. **거부 안내는 발신자에게만.** peer 미접속(`PEER_NOT_CONNECTED`)이나 잘못된 발신자(`INVALID_SENDER`)는 메시지를 중계하지 않고 발신 클라이언트의 송신 채널로만 error 메시지를 push한다. 상대방은 아무것도 받지 않는다.

> **현재 코드 상태(중요).** 이 설계가 명세하는 시그널링 전용 로직(`services/signaling` 패키지, 역할 검증, `PEER_NOT_CONNECTED`/`INVALID_SENDER`)은 아직 **미구현**이다. 현 시점 `internal/interfaces/ws/ws.go`의 `readPump`는 `offer`/`answer`/`ice-candidate`/`control-event`를 **역할 검증 없이 raw 바이트로 그대로 peer에 전달하는 임시 passthrough**(`TODO(step5/6)` 주석)로 동작한다. 본 설계는 그 TODO를 대체할 목표 구조를 정의하며, 이미 구현되어 있는 메시지 래퍼(`ws.Message`), 메시지 타입 상수, Hub 라우팅(`GetPeer`), Coordinator(`Peer`)의 실제 기술 결정을 그대로 옮겨 그 위에 시그널링 분기를 얹는다.

## Implementation Order

전체 구현 순서에서 이 기능은 **5번째**다. WebSocket Handler(#4)의 `readPump` 메시지 디스패치에서 호출되는 형태로 삽입된다.

```
[1] Domain Stores            ✓ (구현 완료)
[2] Room Handler (POST /rooms) ✓
[3] WebSocket Hub            ✓ (internal/services/hub)
[4] WebSocket Handler        ✓ (internal/interfaces/ws — 현재 raw passthrough)
[5] Signaling Protocol       ← 본 설계 (passthrough TODO를 역할 검증 + 중계로 대체)
[6] Control Event Relay
[7] TURN Credentials
[8] CORS Middleware
```

- **선행 의존성:** `#4 WebSocket Handler` — `readPump`의 `switch` 블록, `ws.Message` 파싱, Hub/Coordinator 배선이 이미 존재한다.
- **후행 의존성:** 없음.

## Layer Mapping

| 책임 | 레이어 | 위치 |
|------|--------|------|
| 시그널링 메시지 라우팅 + 역할 검증 + 중계 (유즈케이스) | **services** | `internal/services/signaling` (신규) |
| WS 메시지 타입 상수 (signaling이 export) | **services** | `internal/services/signaling/signaling.go` |
| 라이브 연결 한 쌍·peer 조회 | **services** | `internal/services/hub` (기존) |
| readPump 디스패치 + 바이트↔DTO 직렬화 + 펌프 | **interfaces** | `internal/interfaces/ws/ws.go` (기존, 수정) |
| WS 메시지 래퍼 DTO(`Message`, `ErrorPayload`) | **interfaces** | `internal/interfaces/ws/dto.go` (기존) |
| 구체 타입 생성·주입·라우팅 조립 | **app** | `internal/app/app.go` (기존) |

**depguard 의존 방향 주의:** 의존은 항상 안쪽(domain)을 향한다.

- `interfaces`(`ws`)는 `services`(`signaling`, `hub`)를 import할 수 있다(바깥→안쪽). 따라서 `readPump`의 `switch`에서 `signaling.HandleSignalingMessage(...)`, `signaling.MsgTypeOffer` 등을 참조할 수 있다.
- `services`(`signaling`)는 `interfaces`를 import하면 안 된다. 그래서 시그널링 서비스는 interfaces의 DTO(`ws.Message`)를 알지 못한 채, ws 핸들러가 넘겨준 **메시지 타입(string)과 원본 바이트([]byte)** 만 값으로 받아 처리한다.
- `services`(`signaling`)는 같은 services 레이어의 `hub.Client`/`hub.Role`을 참조한다(동일 레이어 내 의존, 허용).

## Data Structures

### 메시지 타입 상수 (services/signaling — 신규, export)

signaling 서비스가 메시지 타입을 export하여, interfaces 레이어의 `readPump` switch가 `signaling.MsgTypeOffer` 등으로 안전하게 참조한다(매직 스트링 제거, 의존 방향 준수).

```go
// internal/services/signaling/signaling.go
package signaling

const (
    MsgTypeOffer        = "offer"
    MsgTypeAnswer       = "answer"
    MsgTypeICECandidate = "ice-candidate"
)
```

### 기존 WS 메시지 래퍼 DTO (interfaces/ws — 구현 완료)

WS 프레임의 공통 봉투. interfaces 레이어 전용 DTO이며 도메인 타입과 섞지 않는다. signaling 서비스는 이 타입을 **참조하지 않고**(의존 방향) 원본 바이트만 다룬다 — ws 핸들러가 `type` 필드만 파싱해 서비스에 string으로 넘긴다.

```go
// internal/interfaces/ws/dto.go (현행 코드 그대로)
type Message struct {
    Type    string          `json:"type"`
    Payload json.RawMessage `json:"payload,omitempty"`
}

type ErrorPayload struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}
```

### 기존 메시지 타입 상수 (interfaces/ws — 구현 완료)

현재 ws 패키지가 가진 비공개 상수. 시그널링 도입 시 `offer`/`answer`/`ice-candidate`의 **단일 진실 출처는 `signaling` 패키지의 export 상수**로 이전하고, ws 측은 `signaling.MsgType*`를 참조한다. `peer-joined`/`peer-left`/`leave`/`error`/`control-event`처럼 트랜스포트·연결 수명주기 메시지는 ws 패키지에 남는다.

```go
// internal/interfaces/ws/dto.go (현행 코드 그대로)
const (
    msgTypeOffer        = "offer"          // → signaling.MsgTypeOffer 로 대체 예정
    msgTypeAnswer       = "answer"         // → signaling.MsgTypeAnswer 로 대체 예정
    msgTypeICECandidate = "ice-candidate"  // → signaling.MsgTypeICECandidate 로 대체 예정
    msgTypeControlEvent = "control-event"  // Step 6
    msgTypeLeave        = "leave"
    msgTypePeerJoined   = "peer-joined"
    msgTypePeerLeft     = "peer-left"
    msgTypeError        = "error"
)
```

### 기존 라이브 연결 타입 (services/hub — 구현 완료)

signaling 서비스가 발신자·상대방으로 받는 타입. `Role`로 발신자 검증을, `Send` 채널로 중계·에러 push를 수행한다.

```go
// internal/services/hub/hub.go (현행 코드 그대로)
type Role string

const (
    RoleCustomer Role = "customer"
    RoleAgent    Role = "agent"
)

type Client struct {
    Conn   *websocket.Conn
    Role   Role
    RoomID string
    Serial string
    Send   chan []byte // 이 클라이언트에게 보낼 메시지 채널 (버퍼드, cap 256)
}
```

## Interfaces / Contracts

### signaling 서비스의 진입점 (신규)

```go
// internal/services/signaling/signaling.go
package signaling

// HandleSignalingMessage: readPump에서 호출되는 시그널링 메시지 처리 함수.
//   client:   메시지를 보낸 주체
//   peer:     상대방 클라이언트 (nil이면 상대방 미접속)
//   msgType:  파싱된 메시지 타입 ("offer" | "answer" | "ice-candidate")
//   rawBytes: 원본 WS 메시지 바이트 (SDP/ICE 원문 보존을 위해 재직렬화하지 않음)
func HandleSignalingMessage(client *hub.Client, peer *hub.Client, msgType string, rawBytes []byte) error
```

- 입력으로 interfaces DTO가 아니라 **string + []byte + hub.Client** 만 받는다 → services가 interfaces를 모르게 한다(depguard).
- 중계·에러 전송은 모두 `client.Send` / `peer.Send` 채널을 통해 일어난다. 함수는 채널에 넣기만 하고, 실제 WS 쓰기는 interfaces의 `writePump`가 담당한다(레이어 책임 분리).

### 내부 헬퍼 (signaling 패키지 비공개)

```go
// marshalError: error WS 메시지를 바이트로 직렬화.
// {"type":"error","payload":{"code":...,"message":...}} 형태.
// interfaces/ws의 marshalMessage/sendError와는 별개 구현이다(의존 방향 보존).
func marshalError(code, message string) []byte
```

### readPump 디스패치 계약 (interfaces/ws — 수정)

```go
// internal/interfaces/ws/ws.go readPump switch (목표 형태)
switch incoming.Type {
case signaling.MsgTypeOffer, signaling.MsgTypeAnswer, signaling.MsgTypeICECandidate:
    peer := handler.coordinator.Peer(client)
    _ = signaling.HandleSignalingMessage(client, peer, incoming.Type, rawMessage)
case msgTypeControlEvent:
    // Step 6에서 처리
case msgTypeLeave:
    return
default:
    sendError(client, "UNKNOWN_TYPE", "unknown message type: "+incoming.Type)
}
```

> 위는 현행 `ws.go`의 임시 passthrough 분기(아래)를 대체한다:
> ```go
> case msgTypeOffer, msgTypeAnswer, msgTypeICECandidate, msgTypeControlEvent:
>     // TODO(step5/6): role 검증 + services/signaling·relay로 교체.
>     if peer := handler.coordinator.Peer(client); peer != nil {
>         trySend(peer, rawMessage)
>     }
> ```

### peer 조회 계약 (services — 구현 완료)

ws 핸들러는 상대방을 Coordinator를 경유해 얻는다. Coordinator는 Hub의 `GetPeer`로 위임한다.

## Behavior

### 메시지 라우팅 규칙

| 수신 타입 | 발신자 | 수신자 | 검증 조건 | 위반 시 |
|-----------|--------|--------|-----------|---------|
| `offer` | customer | agent | `client.Role == hub.RoleCustomer` | `INVALID_SENDER` |
| `answer` | agent | customer | `client.Role == hub.RoleAgent` | `INVALID_SENDER` |
| `ice-candidate` | 양쪽 | 상대방 | 없음 | — |

세 타입 모두 공통으로 **peer가 `nil`이면 중계하지 않고 `PEER_NOT_CONNECTED`** 를 발신자에게 돌려준다.

### 처리 흐름

```go
func HandleSignalingMessage(client, peer *hub.Client, msgType string, rawBytes []byte) error {
    if peer == nil {
        client.Send <- marshalError("PEER_NOT_CONNECTED", "peer is not connected yet")
        return nil
    }

    switch msgType {
    case MsgTypeOffer:
        if client.Role != hub.RoleCustomer {
            client.Send <- marshalError("INVALID_SENDER", "offer must be sent by customer")
            return nil
        }
        peer.Send <- rawBytes // 원본 JSON 그대로 전달 (재직렬화 금지)

    case MsgTypeAnswer:
        if client.Role != hub.RoleAgent {
            client.Send <- marshalError("INVALID_SENDER", "answer must be sent by agent")
            return nil
        }
        peer.Send <- rawBytes // 원본 JSON 그대로 전달

    case MsgTypeICECandidate:
        peer.Send <- rawBytes // 발신자 역할 무관, 상대방에게 그대로 전달
    }
    return nil
}
```

### offer/answer/candidate 라우팅

- **`offer` (FR-2):** 고객 → 상담원. 발신자가 고객이고 상대방(상담원)이 접속해 있으면 원문을 상담원의 `Send`에 넣는다.
- **`answer` (FR-3):** 상담원 → 고객. 발신자가 상담원이고 상대방(고객)이 접속해 있으면 원문을 고객의 `Send`에 넣는다.
- **`ice-candidate` (FR-4):** 양방향. 발신자 역할 제한 없이 상대방의 `Send`에 원문을 넣는다. 고객→상담원, 상담원→고객 모두 성립한다.

### 역할 기반 발신자 검증 (FR-7 / 비즈니스 룰)

- 상담원이 `offer`를 보내면 → 중계 안 함 + 발신 상담원에게 `INVALID_SENDER`.
- 고객이 `answer`를 보내면 → 중계 안 함 + 발신 고객에게 `INVALID_SENDER`.
- `ice-candidate`에는 역할 검증이 없다.

### 투명 중계(원문 보존) (FR-5 / NFR 투명성)

- `peer.Send <- rawBytes` — `ReadMessage`가 돌려준 **원본 바이트를 그대로** 전달한다. `json.Unmarshal`→`json.Marshal` 왕복을 거치지 않는다.
- ws 핸들러는 라우팅 판단에 필요한 `Message.Type` 한 필드만 파싱하고, `Payload`(SDP/ICE 원문)는 건드리지 않는다.
- 이유: SDP/ICE는 브라우저가 생성·소비하는 불투명 데이터로, 서버가 재직렬화하면 키 순서·공백·줄바꿈 등이 바뀌어 직접 연결이 실패할 수 있다.
- 서버는 시그널링 페이로드를 **저장·로깅·변형하지 않는다.**

### 에러: PEER_NOT_CONNECTED / INVALID_SENDER (FR-6, FR-7 / 비즈니스 룰)

발신자에게만 보내는 error WS 메시지 형식:

```json
{
  "type": "error",
  "payload": {
    "code": "PEER_NOT_CONNECTED",
    "message": "peer is not connected yet"
  }
}
```

- `PEER_NOT_CONNECTED` — 상대방이 아직 세션에 합류하지 않음(`peer == nil`). 어떤 타입의 시그널링이든 중계하지 않고 발신자에게만 안내.
- `INVALID_SENDER` — 역할에 맞지 않는 발신(상담원의 offer, 고객의 answer). 중계하지 않고 발신자에게만 안내. message는 `"offer must be sent by customer"` / `"answer must be sent by agent"`.
- **거부 안내는 발신자(`client.Send`)에게만.** peer의 채널에는 아무것도 넣지 않는다(AC-8).

### 중계 대상 한정

`offer`/`answer`/`ice-candidate` 외 메시지는 이 시그널링 규칙의 대상이 아니다. `control-event`는 Step 6, `leave`는 연결 종료, 그 외는 `UNKNOWN_TYPE`로 발신자에게 에러(ws 핸들러 책임).

### 동시성 안전 (NFR 동시성 / 즉시성)

- peer 조회는 Hub의 `RWMutex` 아래에서 일어나며, LiveRoom은 RoomID 단위로 격리된다 → 세션 간 메시지가 섞이지 않는다.
- `Send`는 버퍼드 채널(cap 256)이고, 실제 전송은 클라이언트별 `writePump` goroutine이 소비한다 → 발신 흐름이 즉시 반환되어 지연 없이 중계된다.
- (참고) interfaces의 `trySend`는 채널이 가득 찬 슬로우 클라이언트의 연결을 끊어 전체를 막지 않는다. signaling 서비스가 직접 `peer.Send <-` 로 넣을지, ws의 비차단 `trySend` 정책을 따를지는 구현 시 정렬한다 — 본 설계는 채널 주입까지를 services 책임, 비차단·연결종료 정책을 interfaces 책임으로 본다.
- `go test -race ./...`로 검증한다.

### 단위 테스트 — `internal/services/signaling/signaling_test.go` (신규)

`hub.Client`에 버퍼드 `Send` 채널만 채운 경량 더블로 검증한다(WS 커넥션 없이 채널만 관찰).

- `offer`(고객 발신, peer 있음) → peer.Send에 원본 바이트가 그대로 들어온다(바이트 동등 비교).
- `answer`(상담원 발신, peer 있음) → peer.Send에 원본 그대로.
- `ice-candidate`(고객→상담원, 상담원→고객 양방향) → peer.Send에 원본 그대로.
- `peer == nil` → client.Send에 `code == "PEER_NOT_CONNECTED"`, peer 측으로는 아무것도 가지 않음.
- 상담원이 `offer` → client.Send에 `code == "INVALID_SENDER"`, 중계 없음.
- 고객이 `answer` → client.Send에 `code == "INVALID_SENDER"`, 중계 없음.
- **원문 보존:** 공백·키 순서가 비표준인 SDP JSON을 넣고, peer가 받은 바이트가 입력 바이트와 byte-for-byte 동일함을 확인.

### 통합 테스트 — `internal/app/integration_test.go` (기존 확장)

`httptest.Server` + 실제 in-memory 조립으로 end-to-end. 기존 `TestWebSocket_RelaysSignalingBetweenPeers`가 이미 raw passthrough(offer→agent)를 검증하므로, 역할 검증 도입 후에도 happy-path가 유지되는지 + 거부 경로를 추가한다.

- 고객 `offer` → 상담원이 동일 메시지 수신.
- 상담원 `answer` → 고객이 동일 메시지 수신.
- 양방향 `ice-candidate` 교환.
- 상담원 미접속 상태에서 고객 `offer` → 고객이 `PEER_NOT_CONNECTED` 수신, 상대 없음.
- 상담원 `offer` → 상담원이 `INVALID_SENDER` 수신, 고객은 아무것도 못 받음.
- 고객 `answer` → 고객이 `INVALID_SENDER` 수신, 상담원은 아무것도 못 받음.
