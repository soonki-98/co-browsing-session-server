# 시리얼로 룸 생성 — 기술 설계도

> 기획: [docs/specs/룸-생성/시리얼로_룸_생성.md](../../specs/룸-생성/시리얼로_룸_생성.md)

## Overview

상담원의 입력값 없는 단일 요청(`POST /rooms`)으로 `RoomSession` 하나와 그에 연결된 `Invitation`(시리얼 → RoomID 매핑) 하나를 atomic하게 발급하고, 시리얼 번호와 만료 시각을 `SuccessResponse[T]` 봉투로 돌려준다.

핵심 기술 결정(실제 코드 기준):

- **huma v2 코드-퍼스트 핸들러**: `http/room.Handler`가 `huma.Register`로 `createRoom` 오퍼레이션을 등록한다. 입력 DTO는 빈 구조체(`CreateInput{}`), 출력은 공통 봉투 `SuccessResponse[CreateData]`(`{"data": {...}}`). 에러는 huma `ErrorModel`(RFC 7807) — `huma.Error500InternalServerError`.
- **유즈케이스 캡슐화**: 시리얼 생성·충돌 재시도·`RoomSession`+`Invitation` atomic 생성·보상 트랜잭션(롤백)은 전부 `services/roomsession.Service.Create`에 모인다. 핸들러는 retry/rollback을 모른다.
- **충돌 재시도(최대 5회)**: 시리얼이 활성 `Invitation`과 겹치면(`invitation.ErrAlreadyExists`) `RoomSession`은 그대로 두고 새 시리얼로 재시도. 5회 모두 실패하면 실패로 처리.
- **보상 트랜잭션(롤백)**: in-memory에는 트랜잭션이 없으므로 `RoomSession`을 먼저 만들고(UUID 충돌 무시 가능), `Invitation` 생성이 비-충돌 에러로 실패하거나 재시도가 소진되면 `roomSessionRepository.Delete(roomID)`로 명시 롤백 → 절반만 만들어진 룸을 남기지 않는다.
- **시리얼 = 외부 용어**: 응답 JSON의 `serial_number`로만 노출. 내부는 `invitation.Serial`(`serialnumber.SerialNumber`). 룸 내부 식별자 `RoomID`(UUID)는 응답에 노출하지 않는다.
- **만료 = 발급 + 10분**: `invitation.InvitationTTL = 10 * time.Minute`. `ExpiresAt`은 `time.Time`(JSON 직렬화 시 ISO8601)으로 UI 카운트다운용.
- **in-memory 저장**: `infrastructure/memory`의 뮤텍스 보호 맵. 서버 재시작 시 초기화.

## Implementation Order

전체 co-browsing 구현 중 룸 생성 슬라이스. 의존은 항상 안쪽(domain)을 향한다.

```
domain (roomsession · invitation · serialnumber)        [선행: 엔티티·포트·sentinel]
   │
   ├─ infrastructure/memory (RoomSessionRepository · InvitationRepository)   [포트 구현]
   │
   ▼
services/roomsession.Service.Create                       ← 지금 여기 (atomic 생성 + 재시도 + 롤백)
   │
   ▼
interfaces/http/room.Handler (POST /rooms, huma)          [DTO 변환 + 트랜스포트 에러]
   │
   ▼
app.New (composition root: 구체 타입 주입 + 라우터 조립)
```

- **선행 의존성:** domain(`roomsession`, `invitation`, `serialnumber`) + `infrastructure/memory` 포트 구현
- **후행 의존성:** 없음 — 독립 엔드포인트. (`Service`의 `Get`/`Activate`/`End`는 WebSocket 연결 슬라이스가 쓰지만, 룸 생성 흐름과는 무관)

## Layer Mapping

| 기획 FR | 레이어 | 담당 유닛 |
|---------|--------|-----------|
| FR-1 (입력 없는 단일 요청 → 룸+시리얼 발급) | interfaces / services | `room.Handler.Create` → `roomsession.Service.Create` |
| FR-2 (대기 상태로 생성) | domain | `roomsession.New` → `StatusWaiting` |
| FR-3 (시리얼 + 만료 시각 응답) | interfaces | `room.CreateData{SerialNumber, ExpiresAt}` (`SuccessResponse[CreateData]`) |
| FR-4 (시리얼 ↔ 룸 연결 보관) | domain / infrastructure | `invitation.New(serial, roomID)` → `InvitationRepository.Create` |
| FR-5 (고유 시리얼, 충돌 시 재발급) | services / infrastructure | `Service.Create` 재시도 루프 + `InvitationRepository.Create` → `ErrAlreadyExists` |
| FR-6 (6자리 시리얼) | services / domain | `serialLength = 6`, `serialnumber.Generator.Generate(length)` |
| FR-7 (절반 생성 금지) | services | 보상 트랜잭션 `roomSessionRepository.Delete(roomID)` |
| FR-8 (실패 시 실패 응답) | services / interfaces | `Service.Create` 에러 반환 → `huma.Error500InternalServerError` |
| 룰 (만료 = 발급 + 10분) | domain | `invitation.InvitationTTL = 10 * time.Minute` |
| 룰 (시리얼 후보 공간 ≈ 34^6) | domain | `serialnumber` `charset`(34자, 혼동 문자 I/O 제외) |
| NFR-1 (동시성 안전) | infrastructure | `sync.Mutex`로 보호되는 맵 |
| NFR-3 (in-memory, 재시작 시 초기화) | infrastructure | `memory.*Repository` (영속화 없음) |

## Behavior

### 핸들러 처리 흐름 — `room.Handler.Create`

```go
func (handler *Handler) Create(ctx context.Context, _ *CreateInput) (*CreateResponse, error) {
	_, createdInvitation, err := handler.service.Create(ctx)
	if err != nil {
		return nil, huma.Error500InternalServerError("failed to create room", err)
	}
	response := &CreateResponse{}
	response.Body.Data.SerialNumber = createdInvitation.Serial.String()
	response.Body.Data.ExpiresAt = createdInvitation.ExpiresAt
	return response, nil
}
```

핸들러는 `RoomSession`은 무시(`_`)하고 `Invitation`만 응답으로 직렬화한다 → `RoomID`(내부 식별자)는 외부에 노출되지 않는다.

### 서비스 흐름 — atomic 생성 + 충돌 재시도 + 보상 트랜잭션

```go
func (service *Service) Create(requestContext context.Context) (*roomsession.RoomSession, *invitation.Invitation, error) {
	// 1. RoomSession 먼저 생성 (UUID는 충돌 무시 가능, 대기 상태)
	roomID := roomsession.NewID()
	newRoomSession := roomsession.New(roomID)
	if _, err := service.roomSessionRepository.Create(newRoomSession); err != nil {
		return nil, nil, fmt.Errorf("create room session: %w", err)
	}

	// 2. Invitation 생성 — 시리얼 충돌 시 재시도 (RoomSession은 그대로 둠)
	for range createMaxRetries {
		serial := service.serialNumberGenerator.Generate(serialLength)
		newInvitation := invitation.New(serial, roomID)

		_, err := service.invitationRepository.Create(newInvitation)
		if err == nil {
			return newRoomSession, newInvitation, nil // 성공
		}
		if !errors.Is(err, invitation.ErrAlreadyExists) {
			// 비-충돌 에러 → 보상 트랜잭션(롤백) 후 에러
			_ = service.roomSessionRepository.Delete(roomID)
			return nil, nil, fmt.Errorf("create invitation: %w", err)
		}
		// 시리얼 충돌 → 재시도
	}

	// 3. 재시도 소진 → 보상 트랜잭션(롤백)
	_ = service.roomSessionRepository.Delete(roomID)
	return nil, nil, fmt.Errorf("create invitation: exhausted %d retries due to serial collisions", createMaxRetries)
}
```

### 보상 트랜잭션(rollback) 근거

두 repository에 걸친 atomic 동작이 필요하지만 in-memory에는 트랜잭션이 없으므로:

- `RoomSession.Create`를 먼저 수행(UUID 충돌 확률 무시 가능).
- `Invitation.Create` 실패(비-충돌 에러 또는 재시도 소진) 시 `RoomSession`을 `Delete`로 명시 롤백 → FR-7(절반 생성 금지) 보장.
- 미래에 영속 저장소로 옮길 때 이 자리에 실제 DB 트랜잭션이 들어옴 — 포트 시그니처/흐름은 그대로 유지(`memory → Redis` 교체는 `app.New`의 주입부만 변경).

### 상태/제어 흐름 (룸 생성 분기)

```
service.Create
  ├─ rsRepo.Create 실패 ──────────────────────────▶ error "create room session: ..."  (롤백 불필요, 생성 자체 실패)
  └─ rsRepo.Create 성공
       └─ 루프 ≤ 5회: gen.Generate(6) → invRepo.Create
            ├─ nil err ─────────────────────────▶ (RoomSession, Invitation, nil)  [성공]
            ├─ ErrAlreadyExists ────────────────▶ 다음 시도 (continue)
            └─ 그 외 err ───────────────────────▶ rsRepo.Delete(roomID) → error  [롤백 후 실패]
       └─ 5회 소진 ───────────────────────────▶ rsRepo.Delete(roomID) → error "exhausted 5 retries ..."  [롤백 후 실패]
```

룸 세션 상태머신(생성 시점): `(생성)` → `StatusWaiting`. (이후 `StatusActive`/`StatusEnded` 전이는 WebSocket 연결 슬라이스 소관 — 본 설계 범위 밖.)

### Sentinel 에러

| 에러 | 선언 위치 | 룸 생성에서의 의미 |
|------|-----------|---------------------|
| `invitation.ErrAlreadyExists` | `domain/invitation` | 시리얼 충돌 → 재시도 트리거 (`errors.Is`로 분기) |
| `roomsession.ErrAlreadyExists` | `domain/roomsession` | RoomID(UUID) 충돌 — 사실상 발생 안 함 |
| (없음) | services | 실패는 `fmt.Errorf(... %w)` 래핑 후 반환 → 핸들러가 `huma.Error500InternalServerError`로 트랜스포트 변환 |

에러 래핑은 `%w`로 체인을 보존하고, 레이어 경계(핸들러)에서 단일 트랜스포트 에러로 번역한다.

### 동시성

- 여러 상담원의 동시 `POST /rooms`(NFR-1): 각 요청은 독립 `RoomID`(UUID)와 독립 시리얼을 받는다.
- `memory.*Repository`의 맵은 `sync.Mutex`로 보호 — `Create`의 "존재 확인 → 삽입"이 원자적이라, 두 요청이 같은 시리얼을 동시에 생성해도 한쪽만 성공하고 다른 쪽은 `ErrAlreadyExists`를 받아 재시도한다.
- `serialnumber.randomGenerator`는 단일 `*rand.Rand`를 공유하므로 동시 호출 시 자체 동기화는 없다 — 검증은 `go test -race`로 한다(아래 Test Plan).

기획 AC를 레이어별 테스트로 매핑한다. 현재 룸 생성 커버리지는 **`internal/app/integration_test.go`**(실제 의존성 그래프를 `httptest.Server`로 띄운 엔드투엔드)에 모여 있다. 도메인 불변식·서비스 재시도/롤백은 별도 단위 테스트로 보강 권장(아래 표의 "권장").

| 기획 AC | 검증 레이어 | 테스트 방식 |
|---------|-------------|-------------|
| AC-1 (성공 응답: 시리얼+만료) | interfaces/app | `POST /rooms` → 200, `data.serial_number` 비어있지 않음 (integration_test `createRoom`) |
| AC-2 (연속 두 요청 → 서로 다른 시리얼) | services/app | `POST /rooms` 두 번 → 시리얼 비교 (권장: 명시 단위/통합 케이스) |
| AC-3 (만료 = 호출 + 10분, ISO8601) | domain/interfaces | `invitation.New`의 `ExpiresAt == IssuedAt + InvitationTTL`; 응답 `expires_at`가 RFC3339 (권장) |
| AC-4 (대기 상태로 존재) | domain | `roomsession.New(...).Status == StatusWaiting` (권장 단위) |
| AC-5 (발급 시리얼로 룸 조회 → 같은 룸) | services/infrastructure | `Create` 후 `invRepo.ResolveBySerial(serial).RoomID == rs.ID` (권장 단위) |
| AC-6 (충돌 5회 초과 → 실패 + 룸 cleanup) | services | mock `Generator`로 같은 값 반복 → `Create` 에러, 이후 `rsRepo.Get(roomID)`가 `ErrNotFound` (권장 단위) |
| AC-7 (실패 시 시리얼/만료 없는 실패 응답) | interfaces | `Service.Create` 에러 → `huma.Error500InternalServerError`("failed to create room"), body에 시리얼 없음 (권장) |
| AC-8 (재시작 시 초기화) | infrastructure | in-memory 저장 — 새 인스턴스는 빈 상태 (구조적으로 보장; `memory.New*` 단위) |
| NFR-1 (동시 생성 안전) | infrastructure/services | 동시 `POST /rooms` N건 → 시리얼 전부 유일, 상태 무손상. **`go test -race ./...`** 필수 |

게이트: 커밋 전 `go test ./...` + `golangci-lint run`(depguard 의존 방향 포함). 동시성(NFR-1)은 `go test -race ./...`. DTO/오퍼레이션 변경 시 `make openapi`로 `docs/openapi.yaml` 재생성, `make openapi-check`로 드리프트 차단.
