# 룸별 연결 관리 — 기술 설계도

> 기획: [docs/specs/실시간-연결/룸별_연결_관리.md](../../specs/실시간-연결/룸별_연결_관리.md)

## Overview

같은 세션(시리얼 코드로 묶인 고객·상담원 한 쌍)에 속한 두 연결을 하나로 묶어, 한쪽이 보낸 메시지가 같은 세션의 상대에게만 전달되도록 하는 연결 관리 계층이다. 서로 다른 세션의 메시지가 섞이지 않게 하는 것이 핵심이다.

구현은 `internal/services/hub` 패키지의 `Hub`로 한다. `Hub`는 모든 활성 룸(`LiveRoom`)을 룸 단위로 관리하는 중앙 주소록이며, 각 `LiveRoom`은 고객 슬롯과 상담원 슬롯 두 자리만 가진다. 한 연결은 `Client`로 표현한다.

핵심 기술 결정:

- **self-contained 서비스**: `Hub`는 도메인·인프라를 import하지 않는다. `RoomID`/`Serial`을 opaque string으로만 다룬다. 시리얼 → RoomID 변환 등 유효성 검증은 호출자(WS 핸들러)가 사전에 수행한다.
- **휘발성 컨테이너**: `LiveRoom`은 실제 WS 연결이 살아 있는 동안에만 존재한다. 두 슬롯이 모두 비면 즉시 맵에서 삭제된다. 서버 재시작 시 사라져도 무방하다(연결과 운명을 같이 함).
- **동시성**: 단일 `sync.RWMutex`로 `liveRooms` 맵 전체를 보호한다. 쓰기 작업(Join/Leave)은 `Lock`, 읽기 작업(GetRoom/GetPeer)은 `RLock`.
- **에러 없음 계약**: 조회 실패·상대 부재는 모두 `nil` 반환으로 신호한다. sentinel 에러를 두지 않는다.
- **슬로우 클라이언트 보호**: `Client.Send`는 버퍼드 채널. 가득 차면 메시지를 버리는 대신 연결을 끊는다(이 정책의 실행은 WS 핸들러 #4 책임, Hub는 채널만 제공).

## Implementation Order

```
[1] Domain Stores ........ (선행, 완료)
        |
        v
[3] WebSocket Hub ........ <== 이 설계도 (룸별 연결 관리)
        |
        v
[4] WebSocket Handler .... (후행: Hub를 주입받아 사용)
        |
        +--> [5] Signaling Protocol
        +--> [6] Control Event Relay
```

- **선행 의존성**: `#1 Domain Stores` (시리얼 → RoomID 해석은 호출자가 처리)
- **후행 의존성**: `#4 WebSocket Handler`, `#5 Signaling Protocol`, `#6 Control Event Relay`

## Dependencies

`Hub`는 services 레이어에 있으나 도메인조차 import하지 않는 self-contained 서비스다. depguard 의존 방향(services → domain만 허용, interfaces/infrastructure/app 금지)을 자명하게 만족한다.

외부 의존성:

```go
import (
    "sync"

    "github.com/gorilla/websocket" // v1.5.3 — Client.Conn 타입에만 사용
)
```

`go.mod`: `github.com/gorilla/websocket v1.5.3`.

호출자(WS 핸들러, #4)가 합류 전에 시리얼을 풀어 `RoomID`를 얻은 뒤 `JoinRoom`에 넘긴다. Hub는 `RoomID`/`Serial`을 opaque string으로만 보관한다.

## Data Structures

### services 레이어 — `internal/services/hub/hub.go`

```go
package hub

import (
	"sync"

	"github.com/gorilla/websocket"
)

// Role은 한 LiveRoom 안에서 클라이언트가 맡는 역할이다.
type Role string

const (
	RoleCustomer Role = "customer"
	RoleAgent    Role = "agent"
)

// Client는 WebSocket 연결 하나를 나타낸다.
// RoomID와 Serial은 opaque string으로만 다룬다 — Hub는 도메인 타입을 알지 못한다.
type Client struct {
	Conn   *websocket.Conn
	Role   Role
	RoomID string      // 속한 LiveRoom의 ID (= roomsession.RoomID 값)
	Serial string      // disconnect 시 Invitation 삭제에 사용 (= invitation.Serial 값)
	Send   chan []byte // 이 클라이언트에게 보낼 메시지 채널 (버퍼드)
}

// LiveRoom은 WS 연결 중인 클라이언트 한 쌍을 담는 휘발 컨테이너다.
// 영속 entity인 roomsession.RoomSession과 같은 ID를 공유하지만,
// 서버 재시작 시 사라져도 무방하다 — 실제 WS 연결과 운명을 같이 한다.
type LiveRoom struct {
	ID       string  // = roomsession.RoomID 값
	Customer *Client // nil이면 아직 미접속
	Agent    *Client // nil이면 아직 미접속
}

// Hub는 모든 LiveRoom을 룸 단위로 관리하는 중앙 주소록이다.
// 도메인이나 인프라를 참조하지 않는 self-contained 컴포넌트다.
type Hub struct {
	mutex     sync.RWMutex
	liveRooms map[string]*LiveRoom // key: RoomID
}

func NewHub() *Hub {
	return &Hub{
		liveRooms: make(map[string]*LiveRoom),
	}
}
```

설계 메모:

- `Client.Serial`은 기존 기술 스펙(03)에는 없었으나 실제 코드에 존재한다. disconnect 시 Invitation 삭제(시리얼 정리)에 쓰이며, opaque string으로만 다뤄 self-contained 원칙을 깨지 않는다.
- 역할(role) zero값은 `Role("")`로, `RoleCustomer`/`RoleAgent` 어느 case에도 걸리지 않아 `switch`의 기본 분기(nil 반환)로 흘러간다.

## Interfaces / Contracts

```go
// JoinRoom은 클라이언트를 LiveRoom에 추가한다. LiveRoom이 없으면 생성한다.
// 동일 role이 이미 접속 중이면 기존 연결을 Close()한 뒤 교체한다.
// 반환값은 상대 role 클라이언트이며, 아직 미접속이면 nil이다.
// Hub는 self-contained이므로 error를 반환하지 않는다(호출자가 사전 검증).
func (hub *Hub) JoinRoom(roomID string, client *Client) (peer *Client)

// LeaveRoom은 클라이언트를 LiveRoom에서 제거한다.
// 양쪽 슬롯이 모두 비면 LiveRoom 자체를 삭제한다.
// 반환값은 상대방 클라이언트로, peer-left 알림 전송에 쓰인다 (nil 가능).
func (hub *Hub) LeaveRoom(client *Client) (peer *Client)

// GetRoom은 roomID에 해당하는 LiveRoom을 반환한다. 없으면 nil이다.
func (hub *Hub) GetRoom(roomID string) *LiveRoom

// GetPeer는 특정 클라이언트의 상대방을 반환한다. 없으면 nil이다.
func (hub *Hub) GetPeer(client *Client) *Client
```

계약 요약:

- 모든 "없음" 상태는 `nil`로 신호한다. sentinel 에러 없음, error 반환값 없음.
- `JoinRoom`/`LeaveRoom`은 상태를 바꾸면서 동시에 알림 대상 `peer`를 돌려준다(조회+변경 원자적 처리).

## Behavior

### 상태머신 — LiveRoom 슬롯 점유

```
            JoinRoom(첫 참여자)
   (없음) ───────────────────────▶ (한 자리 점유, peer=nil)   [대기 상태]
                                          │
                          JoinRoom(상대 역할) │  ▲ JoinRoom(같은 역할)
                                          ▼  │  기존 Conn.Close() 후 교체 (자리 수 불변)
                                   (두 자리 점유, peer=상대)   [묶임 상태]
                                          │
                          LeaveRoom(한쪽)  │
                                          ▼
                                   (한 자리 점유, peer=남은 상대)
                                          │
                          LeaveRoom(마지막) │  peer=nil
                                          ▼
                                   (두 자리 비면 LiveRoom 삭제) ──▶ (없음)
```

### JoinRoom 흐름

```
1. hub.mutex.Lock()  (defer Unlock)
2. liveRooms[roomID] 조회 — 없으면 &LiveRoom{ID: roomID} 생성 후 맵에 등록
3. client.Role로 분기:
   - RoleCustomer: 기존 Customer가 있고 Conn != nil 이면 기존 Conn.Close() → Customer = client → return Agent
   - RoleAgent:    기존 Agent가 있고 Conn != nil 이면 기존 Conn.Close() → Agent = client → return Customer
   - 그 외(zero/unknown role): return nil
```

### LeaveRoom 흐름 (stale client 처리 포함)

```
1. hub.mutex.Lock()  (defer Unlock)
2. liveRooms[client.RoomID] 조회 — 없으면 return nil
3. client.Role로 분기:
   - RoleCustomer: liveRoom.Customer == client 일 때만 Customer = nil; peer = liveRoom.Agent
   - RoleAgent:    liveRoom.Agent == client 일 때만 Agent = nil;    peer = liveRoom.Customer
4. Customer == nil && Agent == nil 이면 delete(hub.liveRooms, client.RoomID)
5. return peer
```

### 동시성 전략 (NFR-1, race 안전)

- `liveRooms` 맵 전체를 단일 `sync.RWMutex`(`hub.mutex`)로 보호한다. 룸별 잠금이 아닌 허브 단일 잠금이다.
- 변경 메서드(`JoinRoom`, `LeaveRoom`)는 `Lock()`/`defer Unlock()`. 조회 메서드(`GetRoom`, `GetPeer`)는 `RLock()`/`defer RUnlock()`.
- 각 메서드는 맵 조회·슬롯 변경·peer 산출을 하나의 임계 영역 안에서 원자적으로 수행한다 → 다른 세션으로 메시지가 새거나 묶임 관계가 어긋날 수 없다.
- `go test -race`로 검증한다(아래 Test Plan 참조).

### 교체 시 stale client 처리 (FR-4, AC-5)

- 같은 역할 재접속 시 `JoinRoom`은 기존 슬롯의 `Conn.Close()`를 호출한 뒤 슬롯을 새 `client`로 덮어쓴다. 자리 수는 그대로 1(한 역할당 한 자리).
- 교체로 밀려난 옛 연결은 닫혔으므로 이후 자신의 읽기 루프가 끝나며 `LeaveRoom(옛 client)`를 호출하게 된다. 이때 `LeaveRoom`은 `liveRoom.Customer == client`(또는 Agent) **동일성 검사**를 거치므로, 이미 새 client가 차지한 슬롯을 잘못 비우지 않는다(`==` 포인터 동일성).

### Client.Send 채널 / 슬로우 클라이언트 (NFR-2, AC-9)

- `Send`는 버퍼드 채널(`make(chan []byte, 256)` 규모). WS 핸들러(#4)의 쓰기 goroutine이 이 채널을 읽어 전송한다.
- 채널이 가득 차면(슬로우 클라이언트) 메시지를 조용히 버리지 않고 해당 연결을 끊는다 — 이 정책의 실행은 #4 WS 핸들러 책임이며, Hub는 버퍼드 채널이라는 메커니즘만 제공한다.

### 에러 처리

- Hub는 외부에 노출하는 sentinel 에러를 두지 않는다. LiveRoom/peer 조회 실패는 `nil` 반환으로 신호한다.
- `Conn.Close()`의 반환 에러는 무시한다(`_ =`) — 교체 시 옛 연결을 닫는 best-effort 동작이다.
- roomID 유효성 검증은 호출자(WS 핸들러)가 `invitation.Repository.ResolveBySerial`로 사전 수행한다.

## Test Plan

테스트는 `internal/services/hub/hub_test.go`에 있다. 테이블 기반 대신 시나리오별 named test 함수로 구성되어 있으며, 동시성 케이스는 `go test -race ./...`로 검증한다.

| 테스트 | 검증 내용 | 매핑 AC |
|--------|-----------|---------|
| `TestJoinRoom_CustomerFirstThenAgent` | 고객 단독 접속 시 peer=nil(대기), 상담원 접속 시 peer=고객, 양방향 `GetPeer` 일치 | AC-1, AC-2, FR-7 |
| `TestJoinRoom_ReplacesSameRoleAndClosesOldConn` | 같은 역할 재접속 시 슬롯이 새 client로 교체되고, 옛 `Conn`은 닫혀 write 실패 (실제 `httptest` WS 연결로 검증) | AC-4 |
| `TestLeaveRoom_ReturnsPeerAndDeletesEmptyRoom` | 퇴장 시 남은 상대를 peer로 반환, 한쪽 남으면 룸 유지, 마지막 퇴장 시 peer=nil 및 룸 삭제 | AC-6, AC-7 |
| `TestLeaveRoom_StaleClientDoesNotEvictReplacement` | 교체로 밀려난 옛 client의 `LeaveRoom`이 현재 슬롯(새 client)을 비우지 않음 | AC-5 |
| `TestHub_ConcurrentJoinLeave` | goroutine 50개에서 3개 룸 × 2개 역할로 Join/GetRoom/GetPeer/Leave 혼합 호출, data race 없음 | AC-8 |

**race 검증 (필수)**: `go test -race ./internal/services/hub/` (전체는 `go test -race ./...`). `TestHub_ConcurrentJoinLeave`가 `sync.WaitGroup`으로 50개 goroutine을 동시에 돌려 `hub.mutex` 보호를 race detector로 확인한다.

테스트 보조: `newTestConn(t)`이 `httptest.NewServer` + `websocket.Upgrader`로 실제 `*websocket.Conn`을 만들어, 교체 시 `Conn.Close()` 동작을 실 연결로 검증한다.
